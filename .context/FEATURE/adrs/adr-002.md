# ADR-002: Keep Role Presets as Setup Helpers Only

## Status

Accepted

## Date

2026-05-19

## Context

The frontend has a role preset select that pre-fills recommended tools for a type of agent. The user can then add or remove tools before saving. Runtime authorization currently still uses hardcoded role matrices in some paths, which conflicts with the desired behavior.

## Decision

Keep role presets for setup only. `/api/ai/tools/presets/{role}` may continue returning recommended tool names, but runtime authorization must not use role presets.

## Alternatives Considered

### Alternative 1: Remove role presets

- **Description**: Delete role-based presets and require fully manual tool selection.
- **Pros**: Eliminates ambiguity.
- **Cons**: Makes agent setup slower and less guided.
- **Why rejected**: Presets are useful as a UI accelerator.

### Alternative 2: Continue authorizing by role

- **Description**: Use role matrices as a second runtime allowlist.
- **Pros**: Adds a guardrail if no tools are saved.
- **Cons**: Creates two sources of truth and hides configuration errors.
- **Why rejected**: Runtime permissions must come from persisted agent configuration.

## Consequences

### Positive

- Presets remain useful without controlling runtime behavior.
- Users can add or remove tools freely before saving.

### Negative

- Preset and saved permissions can diverge by design.

### Risks

- Developers may accidentally reuse `AiPermissionMatrixService` in runtime flows.
- Mitigation: rename or document it as preset-only during refactor.

## Implementation Notes

`AiPermissionMatrixService` should remain reachable only from preset endpoints or setup flows. Runtime services must use `ai_agent_tools`.
