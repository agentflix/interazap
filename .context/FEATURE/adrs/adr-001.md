# ADR-001: Use `ai_agent_tools` as Agent Tool Permission Source

## Status

Accepted

## Date

2026-05-19

## Context

Autopilot currently mixes three sources for agent tools: hardcoded role presets, `metadata.tool_names`, and the existing relational pivot `ai_agent_tools`. This can make the runtime expose or block tools differently from what is configured in the database.

## Decision

Use `ai_agent_tools` as the single source of truth for runtime agent tool permissions. Migrate existing `metadata.tool_names` values into the pivot and remove only the `tool_names` key from `ai_agents.metadata`.

## Alternatives Considered

### Alternative 1: Keep `metadata.tool_names`

- **Description**: Continue storing selected tools in agent metadata.
- **Pros**: Smallest short-term change.
- **Cons**: No FK integrity, weaker tenant-scoped auditing, duplicates the existing pivot table.
- **Why rejected**: The database already has the correct relational model.

### Alternative 2: Create a new permission table

- **Description**: Introduce a new schema for agent tool permissions.
- **Pros**: Could be tailored to future permission attributes.
- **Cons**: Adds unnecessary migration and model churn.
- **Why rejected**: `ai_agent_tools` already models the needed relationship.

## Consequences

### Positive

- Runtime permissions match persisted configuration.
- Tool assignments gain FK integrity.
- Audit and debugging become simpler.

### Negative

- Requires a data migration.
- Existing code that reads `metadata.tool_names` must be refactored.

### Risks

- Unresolvable tool names in metadata may not migrate.
- Mitigation: log unresolved names and preserve unrelated metadata keys.

## Implementation Notes

Create a tenant-aware permission service that reads and syncs `ai_agent_tools`. Controller, snapshot, internal endpoint, and dispatcher flows must use this service.
